# Канал навигации Android → ESP32 HUD, v1

Описание BLE-протокола между Android-приложением `YandexHUD` (GATT central) и
прошивкой HUD (GATT peripheral). Версия контракта — **v1, зафиксирована**.

Нормативный источник — `protocol/spec.md` в общем рабочем пространстве, там же
`protocol/schema/protocol.json` (машиночитаемая схема) и
`protocol/vectors/golden.json` (байтовые фикстуры). Этот документ —
самодостаточная выжимка для работы с прошивкой; при расхождении прав
`protocol/spec.md`.

---

## 1. Транспорт

| Параметр | Значение |
| --- | --- |
| Роли | ESP32 = GATT peripheral, телефон = GATT central |
| Service UUID | `6b1d0001-9c4e-4b7f-a1e2-3f5d6c7b8a90` |
| Характеристика `nav` | `6b1d0002-9c4e-4b7f-a1e2-3f5d6c7b8a90`, `Write` + `Write Without Response` |
| Характеристика `status` | `6b1d0003-9c4e-4b7f-a1e2-3f5d6c7b8a90`, `Notify`, в v1 не используется |
| Advertising | содержит Service UUID; имя `YHUD-ESP32` — в scan response |
| Pairing / bonding | не требуется |
| MTU | приложение просит 247; прошивка работает и при 23 |
| Максимальное сообщение | 197 байт |
| Соединения | одно телефонное подключение |

Правила:

1. Приложение ищет HUD **по Service UUID**, не по имени.
2. `nav` обязана быть доступна **без шифрования и без сопряжения**, даже если
   `BLE_PASSKEY` защищает канал CAN-сниффера.
3. GATT-сервер поднимается независимо от `HUD_DATA_SOURCE` и сосуществует со
   сниффером (dual role). Переключение источника CAN/BLE не должно рвать
   телефонное соединение.
4. В advertising 31 байт: Flags (3) + 128-bit UUID (18) = 21, поэтому имя
   `YHUD-ESP32` кладётся в scan response.
5. `status`/Notify в v1 не реализуются.

## 2. Кодирование

- Все целые — little-endian; `f32`/`f64` — IEEE-754 little-endian.
- `NaN` означает «нет значения». Проверять через `isnan()`, а не по битам.
- Канонический `NaN` у отправителя: `f32` = `0x7FC00000`,
  `f64` = `0x7FF8000000000000`. В .NET `NaN` отрицательный, поэтому кодировщик
  нормализует его в положительную форму.
- `version` = `1` в каждом сообщении. Сообщение с другой версией отбрасывается.
- `type` = `1` или `2`; иное значение — отбросить всё сообщение.
- `sequence` — `u32`, отдельный счётчик на каждый `type`, только для диагностики.
- Тексты — UTF-8 как есть, до 64 байт, обрезка по границе кодовой точки, без
  управляющих символов, переводов строк и эмодзи.
- Полное сообщение до фрагментации — не больше 197 байт.

## 3. Контейнер сообщения

```
off  size  field
0    1     version     1
1    1     type        1 = state snapshot, 2 = position
2    4     sequence    u32 LE, отдельный счётчик на type
6    2     reserved    0 (игнорируется)
8    ..    tlvs        последовательность TLV
N-2  2     crc         CRC-16/CCITT-FALSE по bytes[0 .. N-3], LE
```

CRC: poly `0x1021`, init `0xFFFF`, refin `false`, refout `false`, xorout `0x0000`.
Тест: `crc16("123456789") == 0x29B1`.

- Сообщение короче 13 байт отбрасывается.
- Несовпадение CRC — отбросить сообщение, текущее состояние сохранить.

---

## 4. TLV

```
off  size  field
0    1     group    id группы
1    1     len      длина значения, 0..255
2    len   value
```

- Порядок групп произвольный.
- Каждая группа — не более одного раза; при дубликате побеждает последняя.
- Неизвестная группа пропускается по `len`, остальные применяются.
- Неверная `len` у известной группы отбрасывает **только эту группу**.

---

## 5. Группы

| id | Группа | len | Раскладка / ограничения |
| --- | --- | --- | --- |
| `0x01` | G0 session | 1 | `mode u8`: 0 idle, 1 route, 2 free; иное = группы нет |
| `0x02` | G1 maneuver | 5 | `kind u8`, `distance_m u32`; `kind=0` = группы нет; расстояние 0..2 000 000 |
| `0x03` | G2 lanes | 2..9 | `count u8` (1..8), `lanes u8[count]`; бит 7 — рекомендованная, биты 0..3 — направление |
| `0x04` | G3 next street | 1..64 | UTF-8 |
| `0x05` | G4 current street | 1..64 | UTF-8 |
| `0x06` | G5 speed limit | 1 | `kph u8` (5..200); вне диапазона = группы нет |
| `0x07` | G6 camera | 2 | `distance_m u16` (1..5000); 0 = группы нет |
| `0x08` | G7 road event | 3 | `kind u8` (1..5), `distance_m u16` (0 — не указано, 0..5000) |
| `0x09` | G8 remaining | 8 | `distance_m u32` (0..50 000 000), `time_s u32` (0..3 000 000); оба 0 = группы нет |
| `0x0A` | G9 position | 36 | `lat f64`, `lon f64`, `speed f32`, `bearing f32`, `accuracy f32`, `timestamp i64`; только в `type=2` |
| `0x0B` | G10 meta | 10 | `source u8` (0 notification, 1 screen), `flags u8`, `observed_at_ms i64` |

Кратко по группам:

- **G0** обязательна в каждом `type=1`. `mode=idle` — навигации нет.
- **G1** — манёвр; `kind=0` не отправляется. Держать до 4 с, пока манёвр
  актуален, чтобы стрелка не мигала.
- **G2** — полосы слева направо без пропусков. Биты 4..6 зарезервированы (0).
- **G3/G4** — улицы; пустая строка не отправляется.
- **G5** — только км/ч, 5..200. Пока группа свежая, перекрывает VZE/PSD
  (см. §10).
- **G6** — камера: расстояние 1..5000 м. «Нет камеры» = группы нет, а не 0.
  Разрешена в `mode=free`, запрещена в `idle` и при `rerouting`.
- **G7** — дорожное событие; камера сюда не кодируется.
- **G8** — остаток маршрута: время в пути, не абсолютное ETA. Отправка не
  зависит от согласия на геолокацию.
- **G9** — только `type=2`, ровно одна G9 и никаких других групп. `lat` в
  `[-90, 90]`, `lon` в `[-180, 180]`, `accuracy` — `NaN` или `0 < accuracy <= 100`.
  `bearing` — курс над землёй; может быть `NaN` (на месте). `speed`, `bearing`,
  `accuracy` могут быть `NaN`, такую позицию принимать.
- **G10** — диагностика источника: `source` 0 — уведомления, 1 — экран;
  `flags` бит 0 — экранный ридер подключён.

## 6. Enum

`mode`: 0 idle, 1 route, 2 free.

`maneuver_kind`:

| Значение | Манёвр | Стрелка HUD |
| --- | --- | --- |
| 0 | нет манёвра | — |
| 1 | left | поворот налево |
| 2 | right | поворот направо |
| 3 | left_wide | держаться левее / плавно влево |
| 4 | right_wide | держаться правее / плавно вправо |
| 5 | left_sharp | резко налево |
| 6 | right_sharp | резко направо |
| 7 | u_turn_left | разворот налево |
| 8 | u_turn_right | разворот направо |
| 9 | straight | ехать прямо |
| 10 | finish | прибытие |
| 11 | rerouting | перестроение маршрута, без стрелки и дистанции |
| 12 | roundabout | кольцо; HUD показывает нейтральный символ развязки |
| 13..255 | — | не отправлять, считать «нет манёвра» |

`road_event_kind`: 1 accident, 2 roadworks, 3 closed, 4 hazard, 5 speed_bump.

`lane_direction`: 0 empty, 1 straight, 2 left, 3 right, 4 slight_right,
5 u_turn_left.

## 7. Типы сообщений

### `type=1` — снимок состояния

1. Один цикл — **полный снимок** всех групп, у которых есть данные. Частичных
   обновлений нет.
2. Период: 50..1500 мс; для низкой задержки рекомендуется **~250 мс**.
3. Отсутствие группы = «нет данных». Команд очистки нет. Приёмник не
   экстраполирует.
4. Свежесть — ответственность отправителя: манёвр/маршрут/полосы — не старше
   5 с, камера — 10 с.
5. G1 повторяется до 4 с, пока манёвр актуален, и прекращается, если сменился
   перекрёсток/улица/расстояние.
6. `rerouting`: G1 `kind=11`, без G2 и G6; G8 продолжается.
7. `mode=idle`: G1..G8 не отправляются, G0 — всегда.
8. Камера — только G6; G1 и G6 могут быть в одном снимке.
9. Одинаковые снимки не подавляются: поток кормит watchdog приёмника.
10. Не отправлять готовые строки («через 300 м»), адреса и POI — только числа.
11. Единицы СИ: метры, секунды, м/с; исключение — G5 в км/ч.

### `type=2` — позиция

1. Ровно одна G9, других групп нет.
2. Не чаще 1 Гц.
3. Только при явном согласии пользователя на передачу геопозиции.
4. `bearing` может быть `NaN` — позиция всё равно валидна.
5. `speed` в v1 информационная: HUD показывает скорость только из CAN.

## 8. Фрагментация

Если сообщение не влезает в `MTU - 3`, оно режется на чанки:

```
off  size  field
0    1     frag_magic   0xFA
1    1     frag_index   с 0
2    1     frag_total   1..255
3    ..    data         до (MTU - 6) байт; последний чанк — остаток
```

- Первый байт записи: `0x01` — целое сообщение, `0xFA` — фрагмент.
- Чанки одного сообщения идут подряд с паузой 50 мс.
- Сборка требует одинаковый `frag_total` и `frag_index` с 0 без пропусков;
  иначе частичный буфер сбрасывается.
- Таймаут сборки — 1 с **от последнего принятого чанка** (скользящий).
- CRC проверяется только у собранного сообщения.
- 197 байт — это 12 чанков при MTU 23 и одна запись при MTU 247.

## 9. Тайминги и watchdog

| Событие | Действие приёмника |
| --- | --- |
| Нет валидного `type=1` 3 с | `STALE`, последний снимок сохраняется |
| Нет `type=1` 15 с | очистить зоны G1..G8 |
| G9 старше 5 с | скрыть позицию |
| Ошибка CRC | сохранить текущее состояние |
| Пропуск/повтор sequence | применить как обычно, только диагностика |
| Разрыв BLE | очистить навигацию в течение 1 с |

- Свежесть G9 считается по **времени приёма BLE** (TTL 5 с), а не по
  `timestamp` телефона.
- Для `type=1` отдельных таймеров групп нет: «группа жива» = «есть в последнем
  валидном снимке».
- Приёмник **не экстраполирует** значения: расстояние остаётся из последнего
  снимка до прихода следующего.

## 10. Смешивание с CAN / BAP

Телефон — параллельный слой поверх CAN/BAP. Приоритет — по компонентам, по
наличию группы в последнем валидном снимке:

1. Пока группа есть в снимке, она перекрывает соответствующее поле CAN/BAP.
   Пропала группа или пришёл `mode=idle` — зона возвращается к CAN/BAP.
2. **G5** перекрывает VZE/PSD, пока свежая. Это главный знак; меню HUD
   «Знаки на дороге» и «Ограничение на дороге» управляют только VZE и PSD.
3. **G9** перекрывает штатный GNSS. Скорость телефона информационная: скорость
   HUD и гейт камер — только CAN.
4. **G6** и локальная база `cams.bin` — опция меню: `база` / `телефон` / `оба`.
   Локальная база использует телефонные координаты G9.
5. **G2/G3/G4/G7** в v1 принимаются и хранятся, но не отображаются: в UI нет
   зон полос/улиц/событий. Отправлять их всё равно нужно.
6. Прогресс-бар до манёвра телефоном не заполняется: снимок с телефона скрывает
   бар.
7. Индикатор источника («телефон / BAP / CAN») — только меню и диагностика.

## 11. Golden vectors и проверки

Фикстуры — `protocol/vectors/golden.json`: 10 положительных сообщений
(`idle`, `route_right_300m`, `camera_1000m`, `free`, `far_maneuver_70000m`,
`rerouting`, `position`, `free_camera`, `roundabout`, `position_nan`), фрагментация
`route_right_300m` при MTU 23 (5 чанков) и негативные кейсы (`bad_crc`,
`unknown_version`, `unknown_type`, `unknown_tlv`, `wrong_group_length`,
`duplicate_group`). Обе стороны обязаны воспроизводить байты в байт.

Проверки из корня репозитория:

## 12. Версионирование

`version=1` зафиксирован. Новая версия нужна при изменении Service/
characteristic UUID, имени в advertising, раскладки существующей группы,
смысла enum или контейнера. Без смены версии допустимы только новые группы в
конце диапазона и новые значения enum в конце списка. Неизвестные версии,
типы, группы, значения enum и зарезервированные байты приёмник игнорирует, не
сбрасывая экран.

## 13. Реализация в прошивке

| Файл | Назначение |
| --- | --- |
| `waveshare_hud_mockup/ble_nav_server.cpp/.h` | GATT-сервер, advertising, фрагментация, приём записей, диагностические счётчики |
| `waveshare_hud_mockup/nav_proto.c/.h` | чистый C-декодер: контейнер, CRC, TLV, группы, TTL |
| `waveshare_hud_mockup/nav_proto_generated.h` | сгенерированные константы/enum (не править вручную) |
| `waveshare_hud_mockup/nav_bridge.c/.h` | наложение телефона на `HudData` (G1/G5/G6/G8/G9) |
| `waveshare_hud_mockup/hud_diag.h` | счётчики `nav_snapshots`, `nav_positions`, `nav_crc`, `nav_unknown`, `nav_bad_len`, `nav_groups[]` |

- Включается `HUD_NAV_SERVER_ENABLE` в `hud_config.h`.
- `nav_bridge_apply()` вызывается в `hud_update_cb` после `hud_data_snapshot()`.
- G1 → стрелка/дистанция, G5 → знак, G8 → остаток/время, G6 → блок камер,
  G9 → `gps_lat_e6/lon_e6`, `gps_fix`, `gps_sat`, `gps_hdop_x10`, `gps_hdg_x10`.
- `NaN` bearing не затирает курс машины: `V_HDG` и `gps_hdg_x10` сохраняются.
- Скорость телефона не применяется: `V_SPEED`/`speed_kmh` только из CAN.
- Источник камер — меню `HUD_CAM_SRC` / NVS `camsrc` (`база` / `телефон` / `оба`).
- Диагностические строки: `[nav]` раз в секунду, `[cam]` раз в 2 с при
  включённой локальной базе.
