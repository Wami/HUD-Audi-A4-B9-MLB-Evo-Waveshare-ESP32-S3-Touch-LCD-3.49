## 1. Транспорт

- Роль телефона — **GATT central**, ESP32 — **peripheral** (прошивка поднимает
  GATT-сервер, advertising `YHUD-ESP32`). Приложение фильтрует устройства
  **по Service UUID**, не по имени.
- Service `6b1d0001-9c4e-4b7f-a1e2-3f5d6c7b8a90`, характеристика `nav`
  `6b1d0002-9c4e-4b7f-a1e2-3f5d6c7b8a90`, запись **Write Without Response**
  (предпочтительно), иначе Write.
- После коннекта приложение MUST запросить MTU 247; прошивка корректно работает и
  при MTU 23 (фрагментация §8 черновика: чанки `0xFA` подряд, ≤ MTU−6 = 17 B данных,
  50 мс между записями; сборка на приёмнике с таймаутом 1 с от последнего чанка, §5).
- Pair/bonding не нужен. Характеристика `status` (Notify) **в v1 не реализуется
  с обеих сторон** — связность приложение определяет по факту GATT-соединения.
- При остановке сервиса навигации приложение SHOULD закрывать GATT-соединение,
  а не молчать в установленном (прошивка: disconnect → гашение телефонных зон ≤ 1 с;
  тишина → STALE через 3 с, гашение зон через 15 с по §9.3 черновика).

### 1.1 Сосуществование с существующим BLE-стеком HUD (новое, обязательное)

Сейчас `waveshare_hud_mockup/ble_can_client.cpp` использует NimBLE как **central**
(подключение к CAN-снифферу, UUID `A1B2C3D4-0001-41A2-9E3B-0000000000xx`), а при
`HUD_DATA_SOURCE == HUD_SRC_TWAI` стек вообще не инициализируется. Для телефонного
канала это нужно изменить:

1. GATT-сервер `nav` поднимается **независимо от `HUD_DATA_SOURCE`** и работает
   одновременно с ролью central (dual role).
2. `NimBLEDevice::init(...)` вызывается всегда, когда включён телефонный канал;
   в режиме `AUTO` переключение CAN↔BLE MUST NOT разрывать телефонное соединение
   (`hud_src_twai_active()` не должен отключать GATT-сервер).
3. Лимит соединений задаёт ядро Arduino: `CONFIG_BT_NIMBLE_MAX_CONNECTIONS = 3`
   (проверено в esp32s3-libs 3.3.10) — со сниффером достаточно. API
   `setMaxConnections()` в NimBLE-Arduino 2.5.2 отсутствует, настраивать нечего.
4. Прошивка принимает **одно** телефонное подключение; второе — отклоняет
   (или заменяет предыдущее, но не смешивает состояние).
5. Локальное имя из `NimBLEDevice::init("HUD-3.49")` не совпадает с заявленным
   `YHUD-ESP32`; имя в advertising задаётся явно. Бюджет ADV-пакета учитывает
   обязательный Flags-AD (3 B): Flags(3) + 128-битный Service UUID (18 B) = 21 из
   31 B, полное имя `YHUD-ESP32` (12 B) в тот же пакет не влезает — прошивка
   кладёт его в **scan response** (отдельные 31 B). Приложение MUST искать HUD по
   Service UUID (§1), имя — только для удобства человека.
6. Существующая защита `BLE_PASSKEY` относится только к каналу сниффера.
   Характеристика `nav` MUST быть доступна для записи **без шифрования и бондинга**,
   иначе запись со стороны Android упрётся в pairing-ошибку.
7. Радио-конкуренция: при MTU 23 полный снимок — до 12 записей × 50 мс (~550 мс) на
   том же радио, что ACL-поток CAN. Поэтому MTU 247 — не «пожелание», а целевой режим,
   а отправитель SHOULD держать типичный снимок ≤ 120 B (короткие улицы, без G2 при
   отсутствии полос).

## 2. Общие правила кодирования

- Все целые — little-endian; `f32`/`f64` — IEEE-754 LE. **NaN = «нет значения»**
  по семантике IEEE 754: приёмник проверяет `isnan()` (любой NaN-паттерн), а не
  сравнением битов. **Канонический вывод кодировщика — тихий положительный NaN**:
  `0x7FC00000` (f32), `0x7FF8000000000000` (f64) — он же в golden vectors, чтобы
  байты сходились. В .NET `float.NaN`/`double.NaN` — отрицательный тихий NaN
  (`0xFFC00000`/`0xFFF8000000000000`): приёмник его так же считает «нет значения»,
  но для byte-for-byte совпадения с векторами кодировщик обязан нормализовать NaN
  в положительную форму.
- `version=1` в каждом сообщении; чужую version прошивка отбрасывает. `type`
  вне {1,2} — отбрасывается целиком (раскладка TLV определена только для 1/2).
- Два независимых счётчика `sequence` (u32, по одному на `type`) — только
  диагностика; старт с любого значения, wrap-around нормален.
- Сообщения строго по §4–5 черновика: заголовок 8 B + TLV + CRC-16/CCITT-FALSE
  (тест `crc16("123456789") == 0x29B1`). Полное сообщение ≤ 197 B — кодировщик
  MUST проверять размер до фрагментации.
- Тексты — UTF-8 **как есть, без транслитерации**: шрифт HUD содержит кириллицу
  (RU/EN). ≤ 64 байта, обрезка по границе code point, без управляющих символов,
  переводов строк и surrogate-пар (эмодзи).
- Каноническая таблица групп (полная раскладка — §5 черновика):

| id | Группа | len | Поля |
| --- | --- | --- | --- |
| `0x01` | G0 сессия | 1 | `mode` (0 idle / 1 route / 2 free) |
| `0x02` | G1 манёвр | 5 | `kind u8`, `distance_m u32` |
| `0x03` | G2 полосы | 2..9 | `count u8`, `lanes[count]` (bit7 = рекоменд.) |
| `0x04` | G3 следующая улица | 1..64 | UTF-8 |
| `0x05` | G4 текущая улица | 1..64 | UTF-8 |
| `0x06` | G5 лимит | 1 | `kph u8` (5..200) |
| `0x07` | G6 камера | 2 | `distance_m u16` (1..5000) |
| `0x08` | G7 событие | 3 | `kind u8` (1..5), `distance_m u16` (0 = не указано) |
| `0x09` | G8 остаток | 8 | `distance_m u32`, `time_s u32` |
| `0x0A` | G9 позиция | 36 | `lat f64`, `lon f64`, `speed f32`, `bearing f32`, `accuracy f32`, `timestamp i64` |
| `0x0B` | G10 мета | 10 | `source u8`, `flags u8`, `observed_at_ms i64` |

## 3. Семантика отправки (главное для приложения)

1. `type=1` — полный снимок всех доступных групп, цикл ~750 мс (диапазон
   50–1500 мс). Частичных обновлений состояния нет.
2. **Отсутствие группы = «нет данных»**. Команд clear нет; приёмник ничего не
   экстраполирует. Перестали данные приходить — просто не включайте группу.
3. Свежесть — ответственность отправителя: не слать манёвр/маршрут/полосы
   старше 5 с, камеру старше 10 с (§9.1 черновика).
4. **G1 (манёвр) переотправлять до 4 с**, пока он релевантен
   (`distance_m > 0`, маршрут активен), даже если Навигатор кратко показал
   панель камеры или скрыл balloon — это убирает мигание стрелки на HUD. Если
   манёвр относится к другому перекрёстку (изменились улица/дистанция) —
   удержание прекратить, G1 не слать.
5. При `rerouting` — G1 kind=11, G2 и G6 не слать; G8 продолжает жить.
   При `mode=idle` — не слать G1..G8 вовсе (G0 обязательна всегда).
6. Камера — только G6; в G7 `road_event` значение «камера» не попадает.
   G1 и G6 могут приходить в одном снимке одновременно.
7. `type=2` — ровно одна G9 и никаких других групп; G9 в `type=1` запрещена.
8. **G5**: только км/ч, значения 5..200; вне диапазона — не слать группу
   (не слать `0`). **G6**: `distance_m` 1..5000; «нет камеры» — не слать группу.
   G6 разрешена и в `mode=free` (обзор дороги без маршрута); запрещена только при
   `mode=idle` и `rerouting`.
9. **G9**: `bearing` — курс над землёй (course over ground), а не азимут телефона.
   При остановке Android может отдавать `NaN` — это нормально; приёмник использует
   bearing только если он не `NaN`, иначе берёт курс из CAN/GNSS HUD. Снимок из-за
   `NaN` не отбраковывается. Скорость м/с; частота ≤ 1 Гц.
10. **G8**: `time_s` — остаток маршрута в секундах (не «час прибытия»).
    Абсолютное ETA HUD не вычисляет и не показывает.
11. Согласие пользователя на передачу координат гейтит **только G9**. G8 (остаток
    маршрута) — обычная навигационная группа и передаётся всегда, когда есть
    маршрут. Привязка G8 к разрешению на геолокацию — ошибка.
12. Никогда не слать производные строки («через 300 м», «1 ч 20 мин») — только
    числа; формат и язык — на HUD. Не слать адреса, POI и рекламу из
    уведомлений.

## 4. Свежесть G9 — по времени приёма (принято)

Проверка «timestamp не старше 5 с и не в будущем» сравнивает часы телефона с
часами машины/монотонным временем ESP — при расхождении часов валидная позиция
отбраковывалась бы. Принята редакция:

- **Приёмник определяет свежесть G9 по моменту приёма BLE-записи** (TTL 5 с).
- `timestamp` и `observed_at_ms` — информационные (диагностика), не участвуют в
  отбраковке.
- Отправитель по-прежнему MUST NOT слать позицию старше 5 с по своим часам.
- Проверки `lat ∈ [-90,90]`, `lon ∈ [-180,180]`, `accuracy ≤ 100 м` (если не `NaN`)
  остаются на приёмнике.

## 5. Как прошивка смешивает телефон с CAN/BAP (знать, чтобы не дублировать)

- Телефон — параллельный слой поверх CAN-источника (BAP Navigation_SD,
  VZE/PSD-знаки, GNSS машины). Приоритет **покомпонентный по свежести группы**:
  пока группа телефона присутствует в последнем валидном снимке — она перекрывает
  соответствующее BAP/CAN-поле; как только группа перестала приходить или
  `mode=idle` — зона возвращается CAN/BAP, если он свеж.
- Уточнение терминологии: отдельных per-group таймеров на приёмнике **нет для
  `type=1`**. «Группа жива» = присутствует в последнем валидном снимке; при
  дубликатах снимка зоны не перерисовываются, но watchdog обновляется фактом
  прихода (дедупликацию на отправителе см. §9.2 п.2). Тишина в канале
  обрабатывается только общим watchdog: 3 с → `STALE` (последний снимок
  сохраняется), 15 с → зоны G1..G8 гасятся. Приложению не нужно «догатывать»
  состояние CAN. Позиция — исключение: `type=2` — независимый поток, для него
  свой TTL 5 с от момента приёма записи (§4).
- Буквальная трактовка таймаута сборки фрагментов (§8 черновика, «1 с»):
  прошивка считает **1 с от последнего принятого чанка** (скользящий) — при
  MTU 23 снимок в 12 чанков идёт ~550 мс и BLE-дроппаут посередине не должен
  сбрасывать сборку; потеря среднего чанка всё равно приводит к отбросу по CRC
  или по таймауту.
- Принятые приоритеты на приёмнике:
  - **G5 лимит телефона перекрывает VZE/PSD** (телефон — главный знак, пока группа свежа);
  - **G9 позиция телефона перекрывает штатный GNSS машины** (скорость из G9 —
    только резерв, если скорость по CAN не приходит);
  - **G6 camera vs локальная база cams.bin — настраиваемая опция в меню HUD**
    (телефон / своя база / оба); протокол от этого не зависит.
- G2/G3/G4/G7 в v1 принимаются, валидируются и хранятся в состоянии (< 1 КБ),
  **но на экран не выводятся** (в текущем UI нет полос/текстов улиц/событий) —
  слать по §3 всё равно нужно; отображение включим позже без смены протокола.
  Для интеграционного теста прошивка SHOULD вести счётчики в диагностике
  (`hud_diag`): принято снимков, отброшено по CRC, неизвестных TLV, принятых
  групп по id, отброшено по неверной длине. Иначе отправитель не сможет
  подтвердить доставку групп без экрана.
- Шкала прогресса к манёвру (bar-graph как у BAP 0x12) телефоном не
  заполняется — при телефонном снимке шкала скрыта; отдельного поля в
  протоколе не заводим.
- Значок «источник: телефон / BAP / CAN» — в меню и диагностике HUD, на
  содержимое зон не влияет.

## 6. Соответствие G1 стрелкам HUD (для тестов; норматив — §6 черновика)

| kind | стрелка HUD |
| --- | --- |
| 1 left / 2 right | поворот налево/направо |
| 3 left_wide / 4 right_wide | плавно налево/направо (одна стрелка с «держитесь левее/правее», D2) |
| 5 left_sharp / 6 right_sharp | резкий поворот |
| 7 / 8 u_turn | разворот налево/направо |
| 9 straight | «прямо» (FollowStreet) |
| 10 finish | «прибытие» |
| 11 rerouting | «расчёт маршрута», без стрелки и дистанции |

Разных стрелок для wide/fork не появится без смены версии протокола.

## 7. Фиксация v1 (без bump версии не менять)

1. UUID сервиса/характеристик и имя advertising — как в §1.
2. `version = 1`.
3. Раскладки групп §5 черновика — только additive-изменения (новый id группы,
   новое значение enum в конце списка).
4. Golden vectors §12 черновика — общая тестовая матрица сторон: кодировщик
   обязан воспроизводить сообщения №1–8 байт-в-байт (проверка юнит-тестом на
   обеих сторонах).
5. Дополнение к общей матрице (редакция 2): добавить два вектора, которых не было
   в первой редакции черновика —
   - `type=1`, `mode=free` + G4/G5 + G6 (камера без манёвра): проверяет, что камера
     в обзоре дороги не гасит текущую улицу и не требует G1;
   - `type=2`, G9 с `NaN` в `speed` и `bearing`: проверяет канонический тихий NaN и
     то, что позиция с `NaN` не отбраковывается.
6. Новая группа/значение enum — только в конец диапазона; получатель обязан
   игнорировать неизвестное.

## 8. Чек-лист приложения перед интеграцией

- [ ] Кодировщик: контейнер / TLV / CRC / фрагментация — golden vectors §12
      byte-for-byte (юнит-тест).
- [ ] MTU 247 запрошен; при отказе — корректная фрагментация под MTU 23
      (сообщение №2 собирается в 5 чанков).
- [ ] Цикл `type=1` ~750 мс; `type=2` ≤ 1 Гц; G9 только в `type=2`; G0 в каждом снимке.
- [ ] Удержание G1 ≤ 4 с; «нет данных = нет группы»; без производных строк;
      SI-единицы (м, с, м/с; G5 — км/ч).
- [ ] G8 не зависит от согласия на координаты; гейтится только G9.
- [ ] Камера разрешена в `mode=free` и запрещена при `idle`/`rerouting`.
- [ ] `bearing` может быть `NaN`; снимок не отбраковывается.
- [ ] Разрыв GATT при остановке сервиса; foreground service против Doze
      (иначе STALE/гашение зон по §9.3 — ожидаемое поведение).
- [ ] Приватность: G9 только с явного согласия пользователя; никаких
      адресов/POI; курс и координаты не логируются.

## 9. Закрытые вопросы (редакция 1 → ответы отправителя)

1. **Свежесть G9 по времени приёма** — подтверждено, перенесено в §4.
2. **Частота `type=1` на стоянке** — остаётся ~750 мс. Отправитель шлёт каждый цикл
   без дедупликации и без проверки движения (`HudService.cs`, цикл 50–1500 мс);
   тишины не будет, пока передача включена. При MTU 23 цикл может растянуться до
   ~1 с из-за фрагментации — это нормально, приёмник переживает (сборка: 1 с от
   последнего чанка, §5). Отправитель MUST NOT «оптимизировать» молчанием
   одинаковых снимков: периодичность кормит watchdog приёмника; подавление
   перерисовки дублей — обязанность приёмника (§11.2.3 черновика, уже зафиксировано).
3. **G6 при `mode=free` без маршрута** — да, будет. Код считает `driving` для
   `route` и `free`; камера не отправляется только при `idle` и `rerouting`.
   Добавлено в матрицу §7.5 и в чек-лист §8.
4. **Второй источник (Яндекс Карты)** — не планируется, правило проекта: источник
   только `ru.yandex.yandexnavi`. Если когда-нибудь появится — новое значение
   `source` в G10 (additive, без bump).

## 10. Проверить на железе (после реализации)

- [ ] Dual role: телефон подключён, CAN-сниффер подключён одновременно.
- [ ] `HUD_SRC_TWAI` и `HUD_SRC_AUTO`: GATT-сервер доступен, переключение источника
      не рвёт телефонное соединение.
- [ ] Запись в `nav` без pairing при включённом `BLE_PASSKEY` для сниффера.
- [ ] Advertising содержит Service UUID; приложение находит HUD по UUID.
- [ ] MTU 247 согласуется; при принудительном 23 снимок 197 B приходит 12 чанками
      без потерь.
- [ ] Второе телефонное подключение отклоняется.
- [ ] CAN-поток не деградирует при телефонной записи раз в 750 мс.
